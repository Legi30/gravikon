# CLAUDE.md

## Repository Purpose

**Gravitační schůzkovač (Gravikon)** is an interactive web application for scheduling meetings between celestial bodies in a planetary system. It accounts for relativistic effects including signal delay (due to finite speed of light) and time dilation (caused by gravitational curvature). The app features a procedurally generated planetary system visualizer and a meeting planner that calculates relativistic time effects for participants on different celestial bodies.

## Tech Stack

- **Ruby**: 3.4.5
- **Rails**: ~8.0.2
- **Database**: SQLite3 (>= 2.1)
- **Web Server**: Puma (>= 5.0)
- **Asset Pipeline**: Propshaft with Terser (JS minification) and CSSO (CSS minification)
- **Caching/Queue**: Solid Cache, Solid Queue, Solid Cable
- **Deployment**: Kamal (Docker-based), Thruster (HTTP compression)
- **Testing**: Minitest (Rails default)
- **Code Quality**: RuboCop Rails Omakase, Brakeman
- **Libraries**: Nokogiri (SVG generation), JSON (data parsing)

## Build & Run

```bash
# Install dependencies
bundle install

# Initialize database
rails db:create db:migrate

# Generate initial planetary system data
ruby lib/generator.rb 4 2

# Generate SVG visualization
ruby lib/visualizer.rb

# Start development server
rails server

# Access at http://localhost:3000
```

## Security

- **Brakeman**: Static analysis for security vulnerabilities included in development/test gems
- **Credentials**: Encrypted credentials stored in `config/credentials.yml.enc` with master key in `config/master.key`
- **Database**: SQLite3 for local development; consider PostgreSQL for production
- **CSRF Protection**: Built-in Rails CSRF protection enabled by default
- **Code Execution**: `SystemsController` uses `system()` calls to execute `lib/generator.rb` and `lib/visualizer.rb` - ensure proper input validation if parameters are ever exposed
- **Docker**: Dockerfile provided for containerized deployments with Kamal

**Recommendations for production:**
- Enable HTTPS/TLS
- Implement user authentication if multi-user access required
- Sanitize file paths in JSON data loading
- Add rate limiting for system regeneration endpoints
- Review and restrict system command execution

## Data

**Primary Data Sources:**

1. **`data/system_data.json`**: Planetary system configuration
   - Generated by `lib/generator.rb`
   - Contains celestial bodies (star, planets, moons) with:
     - Position (x, y coordinates)
     - Physical properties (radius, density, mass)
     - Time dilation factor
   - Visualized by `lib/visualizer.rb` → `public/system.svg`

2. **Database Tables**:
   - **meetings**: Stores scheduled meetings
     - `start_time`, `end_time`, `topic`
     - `participants` (JSON array of celestial body names)
     - `local_avg_duration` (time-dilated meeting duration)
     - `avg_delay` (signal delay between participants)

**Data Flow:**
- Generator creates system → JSON file → Visualizer creates SVG
- User creates meeting → Calculates relativistic effects → Stores in DB
- System regeneration deletes all meetings and recreates planetary data

## Conventions

**Code Style:**
- Follow **RuboCop Rails Omakase** style guide
- Run `rubocop` before commits
- Use `.rubocop.yml` for project-specific configurations

**File Organization:**
- `lib/` - Custom Ruby scripts (generator, visualizer)
- `data/` - JSON configuration files
- `public/` - Static assets (generated SVG)
- `app/` - Rails MVC structure

**Naming Conventions:**
- Controllers: PascalCase (e.g., `MeetingsController`, `SystemsController`)
- Models: Singular PascalCase (e.g., `Meeting`)
- Routes: RESTful resource routes
- Czech language in UI, comments, and topic field

**Database:**
- Use migrations for all schema changes
- Keep schema in `db/schema.rb` under version control
- Foreign keys and indexes for production scaling

**Git Workflow:**
- Keep `.gitignore` updated (excludes `log/`, `tmp/`, `storage/`, `.workspace/`)
- Use descriptive commit messages
- Master key (`config/master.key`) should remain private

**Development Practices:**
- Validate JSON structure when reading `system_data.json`
- Handle edge cases (e.g., fewer than 2 participants)
- Use Rails helpers for form building and sanitization
- Document complex physics calculations with inline comments
